# Start with the information already available

On invocation, read the request and any existing workspace brief before asking questions. Give a short opening in the user's language that distinguishes:

- **Known:** the dataset/location, direction if any, supplied papers, existing scope or permissions and requested budget. Mention only what has actually been supplied or verified.
- **Needed now:** an accessible dataset or a location the host can reach, and any unresolved fact that changes the next action. If nothing essential is missing, say so and start.
- **Optional, with a benefit:** a direction or seed focuses the search; local PDFs provide starting examples; known publications and ongoing work help avoid duplication; priorities or a time/usage budget guide effort. No direction and no PDFs are valid starting points.

Keep this proportional to the request; do not display an empty form or repeat a long checklist when the user has already supplied enough. For example, with an accessible data folder and established permissions: “I have the dataset and planning scope. No further input is needed to start. A direction, paper folder or time budget would help focus the work if you have one; otherwise I’ll begin with the data and existing research.”

## Choose a useful working context

For continuing research, keep useful conversation history and read `brief.md`, `recommendations.md`, `NEXT.md` and their linked evidence to recover current questions, decisions, permissions and known unknowns. The same notes support resuming in another native host chat when convenient; a restart is not required.

When the user wants independent discovery after a conversation heavily focused on old candidates, recommend a fresh native host chat. Carry authorized data locations, scope, user intent, verified dataset facts, unresolved measurement limits, relevant prior outcome exposure and owner answers, including “unknown.” If the user wants an unanchored search, leave earlier candidate answers and verdicts out of its starting packet, preserving them for deliberate later comparison. Respect the user's choice to reuse history; do not erase useful evidence or require a fresh start.

Inherit the host's current model and effort. For demanding discovery, the user can choose a stronger available host model or more effort within their budget; this can add capability but cannot supply missing evidence or guarantee better questions. Do not silently change settings or model services.

## Ask only what changes the work

Check authorized local documentation, file structure and a small readable sample for facts the host can discover. Do not ask the user to inventory fields, choose methods, define an estimand or write a research protocol before discovery. Ask owner-only scientific questions when inspection exposes a consequential ambiguity, linking the concrete evidence and affected question.

Group the few unresolved questions that matter now into one concise message. Mark essential answers separately from optional ones and explain the benefit of each optional input. Reuse earlier answers and permissions; do not reopen resolved questions on continuation. If the user has no direction, begin broad dataset reconnaissance and prior-use research instead of requiring them to choose a topic.

When no dataset or usable location is available, request one. Existing papers or a supplied topic can still support preliminary literature work, but cannot establish that a particular dataset can answer a question. If one modality, owner fact or resource is missing, continue the unaffected inspections and candidate work; identify which judgments remain conditional. Never invent absent answers or treat silence as permission.

## Carry scope into the work

Apply the [default planning scope](../../dataset-card/references/generic-probes.md#default-planning-scope). Reuse the user's access and transmission permissions. Ask only about an unresolved permission needed for a particular action; a dataset path or plugin installation does not grant new transmission, reserved-data or service access. While that action waits, continue work allowed by the established scope.

Authorized outcome counts, distributions, missingness and coverage may inform planning. Keep candidate target-effect tests, significance searches, full analyses and confirmation outcomes outside discovery. Record prior exposure if a later question targets an inspected summary. An unspecified budget does not block an already-authorized bounded first inspection; resolve a budget before extended or delegated live work, or when the host or task requires one. Do not select another model service implicitly.

Save the useful intake in ordinary prose in `research/<dataset>/brief.md`: verified inputs and their sources, the user's preferences, applicable permissions, unresolved facts and the work each limits. Record “no direction supplied” or “budget unspecified” when true; do not supply a fictional answer. Update the notes when an answer arrives and revise only the affected work. Keep this a conversation and a readable research note, not a required form or an application state machine.
